# GPUI Windows ByteVC2 直接播放方案

## 目标与范围

GPUI Windows 在选中 ByteVC2 时，直接显示 vvdec 解出的画面并播放原音轨，不生成 H.264 兼容文件。普通编码继续使用现有系统播放器。本方案先覆盖 Windows；macOS 的播放器实现和验证另行设计，不把 Windows 结果外推到其他平台。

## 当前边界

- `hongguo-bytevc2` 已能从明文 MP4 解出带可选 PTS 的 8-bit YUV 420 帧，但当前输入为文件，解码从头顺序进行。
- `hongguo-stream` 已提供可取消的明文 Range 读取，在线输入可以复用；它不是现有文件解码接口的直接替代品。
- Windows 的 `MediaEngine` 负责声音、播放时钟和视频帧；视频经 D3D11 纹理与 GPUI 同画布。不能只把 vvdec 回调接到画布就认为实现了播放器。
- 转码缓存及合并、下载路径服务于其他用途，直接播放不应改写它们的语义。

## 方案

1. 在播放器契约之下增加 ByteVC2 播放实现，GPUI 仍通过 `hongguo-player` 门面和 `PlayerLike` 控制；由选中的流编码决定播放器实现。业务服务继续负责选流与解密供数，播放器不反向依赖壳。
2. 将 ByteVC2 样本读取扩展到可取消的随机访问输入，接入本地文件与 `hongguo-stream` 的明文范围读取。按样本表和时间戳送 vvdec，使用有界帧队列；切集、seek 和销毁必须取消旧读取及解码，防止旧帧回流。
3. 在 Windows 播放实现中把解码帧转换/上传到渲染设备可采样的纹理，复用现有视频 quad 和舞台几何。明确 YUV 色彩空间、范围、步幅及设备重建语义，不能默认 CPU 上传零拷贝。
4. 以实际音频输出进度作为主时钟，按视频 PTS 调度和必要时丢弃过期帧。先验证 Media Foundation 可否可靠地从当前来源单独播放音频并提供时钟；若不能，设计明确的音频解码与输出路径。不得在技术探针完成前假定 MediaEngine 能忽略 ByteVC2 视频轨。
5. 实现暂停、恢复、拖动、倍速、音量、静音、时长和结束事件。seek 从可解码的随机访问点重新建解码状态并丢弃目标前的画面；样本表是否提供足够的随机访问信息须先验证。

## 验证与停点

- 先做本地 Windows 技术探针，使用真实的 ByteVC2、音轨与时间戳样本，验证音频时钟、纹理上传、关键帧 seek、帧顺序和资源释放；若平台接口不支持预期路径，先更新方案再实现。
- 自动测试覆盖 PTS 排序、队列上限、取消、seek 代次、音视频调度和 EOF；样本必须覆盖 B 帧、无音轨和时间戳缺失等边界。
- Windows 真机验收：冷启动、首帧、连续播放、暂停/恢复、进度跳转、1×/2×、音量/静音、切集/切剧、网络中断恢复、窗口缩放/最小化、切回普通编码；确认无旧声音或旧画面残留。
- 在相同真实样本和机器上对照现有 H.264 兼容链，记录首帧耗时、CPU/GPU、内存、丢帧和音画偏差；直接播放不得生成 H.264 兼容成品。
- 验证目标为 Windows；macOS 实现和跨平台一致性不在本阶段声称完成。
