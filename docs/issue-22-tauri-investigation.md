## 结论

这个 issue 包含多个独立缺陷：启动注册长期占住播放、鉴权错误归类不当、历史目标越界、末集决策依赖未就绪数据、失败时恢复入口消失、刷新导致原生窗态与前端失配，以及登录后的历史查询忽略本地新记录。不能用一个播放器补丁解释全部反馈。

原用户的 `101108: USER_NOT_LOGIN` 缺少同设备请求与响应，具体鉴权拒绝原因尚未确定。登录云历史的集号偏移已由真实回环确认：登录上报误用了匿名的 1 基编号；云端保存该值，列表按既有 0 基口径加一后越界。恢复登录写侧减一后，同一真实 vid 的发送、云端原始值、解析值和更新时间均已对应。

随后用户手动播放《龙庭序列》末集 504，却仍看到历史停在第 2 集 00:05。日志确认末集已按 503 正确上报，而随后的云列表仍是旧行；原 Tauri 查询登录时只显示云历史，且记录后的失效不重拉活跃查询，使本地已保存的新进度无法及时参与展示。当前已统一查询并按更新时间选取完整历史行，没有增加存储或修正云编号。

## 阻断项

### 1. 注册生命周期被当作播放的单一就绪信号

依据：`机制根治不打补丁`、`并发任务有主`、`日志为排查服务`。

源码链路：

- `crates/hongguo-tauri/src/bootstrap/device.rs` 启动注册任务。
- `crates/hongguo-service/src/device.rs:765` 的 `ensure_registered` 持有 `ReleaseOnDrop`。
- `crates/hongguo-service/src/cold_start.rs:26` 只等待布尔意义的放行，没有成功、失败、阻断原因。
- `crates/hongguo-service/src/device.rs:466` 配置重试间隔 60 秒、最多 30 次；注册 HTTP 单次超时 8 秒。
- `crates/hongguo-service/src/play_service/online/prepare.rs:89` 和 `play_service/local.rs:193` 等待门闩后才取流。
- `src/service/tauri/invoke.ts:33` 直接等待 `invoke`，没有规范文档描述的 30 秒超时。

按每次请求耗尽 8 秒估算，注册阶段约为 `30×8 + 29×60 = 1980 秒`，即 33 分钟量级。DNS 立即失败时会短一些。已有 `ReleaseOnDrop` 会在退出时放行，因此不能把它描述为“所有错误路径永久死锁”。但它会把几十分钟的恢复任务放在用户一次播放请求的关键路径上，且最终失败也只放行、不传失败原因。

SDI 交换不在这把注册门闩内；它和首次材料准备是门闩后的独立取流阶段。给 `wait()` 几秒超时然后继续用未注册身份取流，既不能修复注册失败，也会隐藏真实错误。

另一个“放行后仍失败”的可能路径是持久注册限制：`register/attempt.rs:296` 对非 2xx、且非 408/5xx 的响应进入限制分类；没有有效重试时间时可能形成 manual 限制。`device.rs:718` 在重启后继续遵守它，网络放行不会解除。原用户是否命中这条路径尚无证据，修复时应保留限制并明确展示原因。

已有 `device_status`、`device_retry_register` 命令和 `bootstrap/device.rs:10` 的 `DeviceStatus`，但前端没有消费入口；现有状态也没有注册进行中、下次重试时间和阻断状态。应补齐现有接口，避免再造独立注册入口。

### 2. 取流错误丢失语义，重试策略无法作正确决策

依据：`错误处理按项目约定`、`禁无依据兜底`、`验证不过度`。

- `crates/hongguo-common/src/utils/json.rs:23` 把小写 `code != 0` 统一归为 `AppError::Media`；`hongguo-api/src/play_url.rs:226` 调用它。截图中的鉴权拒绝因此被提示成需要重新下载。
- `src/locales/zh-CN.json:577` 的媒体错误文案确实是“视频处理失败，请重新下载这一集”。
- `hongguo-service/src/play_service/local.rs:88` 将部分失败放入成功返回的 `PlayResponse.error/errorKind`，而此前的解析失败走 IPC reject。
- `src/features/player/hooks/use-playback-source.ts:180` 在成功返回错误时主要识别编码不支持；`:203` 在 IPC reject 时主要识别材料校验错误。错误策略分成两路，其他确定性失败都可能进入自动重试。
- 同文件 `:112` 的重试没有总次数上限：前四次快退避，之后每 30 秒继续。`NotFound` 会不断重试一个不存在的集；`Auth` 也不会因重复相同请求自动修复。

`101108` 的根因仍需确认发生在哪一段身份/会话/请求上。不能把“登录”或“重新下载”作为已证实的解决办法。当前 dev 的匿名注册、MetaSec、cold-start 链路与 `v0.6.6` 没有解决此反馈的行为差异。

### 3. 历史记录与实际播放目标脱节

依据：`不臆造`、`契约两端同源`、`机制根治不打补丁`。

- `crates/hongguo-api/src/history/mod.rs:85` 对列表中的 `vid_index` 无条件加一。
- 同文件 `:343` 的更新请求直接使用领域内 1 基集号。`c1eceddf` 将登录上报从减一改成直接传集号，读侧加一未同步改变。
- 文档仍有 list/delete 为 0 基的约定，历史页源码却认为云端集号为 1 基，现有描述互相矛盾。
- `src/pages/history/components/history-page.tsx:116` 已成功 resolve 剧集，却丢弃返回的分集表和历史 `vid`，只对 `item.vidIndex` 做下限钳制后起播。
- `crates/hongguo-service/src/play_service/local.rs:40` 无法在重新解析的档案中找到第 129 集，返回的错误与附图一致。
- `src/stores/player.ts:85` 在起播成功前就保存目标，错误目标还会成为持久恢复目标。这个播放器目标不等于已经证明云历史由它写坏。

以上为初轮源码定位。后续用户授权登录实测发现，同一账号既有第 13 集的正确云原始编号为 12，而修复前本客户端刚播放的末集 786 被云端保存为 786、客户端解析为 787；第二季首集同样出现原始 1、解析 2。因此不能删除列表加一，而应只修登录写边界。`c1eceddf` 把匿名实抓的 1 基上报外推到登录上报，是本轮复现的写入错误来源。修复后相同末集/首集的云原始值为 785/0，解析为 786/1，且更新时间与本次上报一致。已有入口继续按真实 `vid` 校验，避免存量错误编号进入播放请求。

### 4. 末集与跨季接力把未就绪资料当作有效空值

依据：`禁无依据兜底`、`单一路线`。

- 播放与前端分集查询独立并行；后端可以自行解析档案后起播，因此视频可播放不代表前端 `currentSeries` 已就绪。
- `src/features/player/components/player-page.tsx:393` 用 `episodes.length ?? 0` 判断末集。
- `src/features/player/hooks/use-binge-relay.ts:94` 再用相同逻辑计算并提交 `vidIndex + delta`。分集查询未完成或失败时，第 100 集可以直接进入第 101 集。
- 同文件 `:48` 将相关季查询未完成/失败同样当成空列表，提前切到其他推荐，无法等待真正的下一季。

有完整分集表且集号连续时，第 100/100 集会走 `advanceAfterSeriesEnd`，所以“任何末集必然加一”不是事实。修复需要覆盖缺失、失败、非连续集号及跨季资料的决策语义。

### 5. 错误页失去恢复入口，窗口镜像还会在刷新后失配

依据：`窗口级状态真值在后端`、`机制根治不打补丁`、Web UI 的错误路径可恢复要求。

- `src/features/player/components/player-page.tsx:439` 的有源分支包含 `:568` 的 `PlayerStageChrome`；取流失败或重试清空源时，退出迷你、选集等操作随它卸载。
- `player-recovery-ui.tsx:28` 的替代界面没有传递退出连播能力；`immersive-info-overlay.tsx:38` 的相关操作因此不显示，迷你模式还会主动隐藏它们。
- `src/features/player/hooks/use-player-interactions.ts:124` 在处理 Escape 和方向键前就因缺少 video 返回；`AppShell` 同时隐藏迷你模式下的应用导航。
- `crates/hongguo-tauri/src/commands/window_cmd.rs:20` 的 `MINI_RESTORE` 在 Rust 进程中保留；WebView 刷新后 `src/stores/ui.ts:42` 将 `miniScreen` 重置为 false，且不持久化它。启动只回读全屏，没有回读 mini/portrait 等原生模式。
- `use-mini-window.ts:46` 先改前端状态再异步发命令；退出失败被吞。全屏退出、竖屏退出和进入迷你也没有串行等待。
- `window_cmd.rs:246` 起多处窗口操作忽略失败并返回成功；只调整前端 `.then()` 仍无法保证原生窗口与镜像一致。

### 6. 登录历史查询丢掉本地新记录，并使活跃页面停留在旧云结果

依据：`机制根治不打补丁`、`同一段逻辑只有一个明确归属`、`诚实报告`。

用户在测试 App 中自行将《龙庭序列》（`7698639495289113662`）切到末集 504 播放完成。受限筛选日志确认，末集 `vid=7702485557221280793` 在 `1794577057294` 按领域 504→线上 503 上报，位置为 113986 毫秒；`13:37:41Z` 的云列表仍回旧 `vid=7698661809829448729`、线上集号 1，即客户端第 2 集。用户截图的 2/504、00:05 与旧行一致，不能归为末集没有上报或云端自动加一。

原 `HistoryPage` 登录后只选云列表；首页和详情也各自使用云历史。现有本地历史已保存新行，却只在匿名模式参与显示。`use-playback-progress.ts` 的记录完成回调使用 `invalidateQueries({ refetchType: 'none' })`，不会重拉已经挂载的历史查询；`useWatchHistory` 又使用统一的 10–30 秒缓存时效。云列表暂时可见旧行时，界面缺少采用本地新记录的统一决策。

现有持久数据仍只有同一份本地历史。初版在 Tauri 查询层合并，后续按用户要求迁入公共 Rust `history_service::list`，Tauri 的 `useWatchHistory` 与 NSH 的历史页、个人内容源共用这一结果。登录查询以 `seriesId` 去重并取 `updatedAtMs` 较大的整行，同刻本地优先；不取最大集号或最大进度，允许回看更早集，保证 vid、集号和位置来自同一条记录。公共服务最终对已知总集数的超集记录截断集号，且不回写原数据。记录完成后刷新活跃查询，公共删除入口同步清理既有本地记录。没有增加持久表、批量迁移或定时轮询。

## 一条推荐修复路线

以下按依赖顺序落地，每步只修改 Tauri 及其实际使用的业务边界；共享 service/API 仍保持无 UI 框架依赖。

### A. 明确启动就绪与失败，不把长期重试绑在一次播放上

1. 在 service 的启动注册协调处维护可订阅的状态：等待、就绪、已安排重试、受限、失败，以及失败原因和现有重试计划。不要继续用“任务结束即 READY”代表注册成功。
2. 首轮注册失败后，一次播放及时收到对应的网络/注册限制错误。瞬态失败的后续恢复由同一个后台任务负责，沿用同一轮注册材料、既有次数上限和限制判定；前端重试只订阅/请求该任务，不另开并发注册。
3. 已有有效注册档案直接复用。注册限制只禁止新注册，不阻断有效旧档案继续取流；独立展示其限制。只有缺少可用身份时，才因显式拒绝、限流或本地限制停止在线准备。只有身份确实就绪时才进入 MetaSec/取流，禁止超时后以匿名空身份继续。
4. 扩展现有 `DeviceStatus` 和设备状态/重试命令，提供启动状态快照及状态变化；页面明确注册状态并始终允许离开和切换目标。切集使旧回调失效，后台任务不再占住前台完整恢复周期；请求级 IPC 取消不在本次已确认修复范围。
5. 接通 service 事件、Tauri 转发、前端事件名及 zod schema；注册成功沿用已有事件触发恢复。诊断记录阶段、耗时和脱敏错误，不落 cookie、token 或签名 URL。

涉及：`cold_start.rs`、`device.rs`、`bootstrap/device.rs`、播放调用点、事件契约和播放器恢复 UI。

### B. 统一播放失败分类与恢复策略

1. 在取流响应边界识别已证实的鉴权业务码，保留原业务码和发生阶段；不要修改所有 API 的通用 `check_code` 来猜测未知错误，也不要改写 signer。
2. 在播放器一个入口将 `PlayResponse.errorKind` 和 IPC reject 归一为同一失败模型，界面与重试共用判定；不再只保存一个错误字符串。
3. 仅对瞬态网络、断供等可恢复错误作有总预算的自动重试。鉴权失败等待身份/会话状态改变；集不存在转为重新选集；材料校验、编码不支持等确定性失败停止自动重试。
4. 错误页提供与原因一致的动作。在线鉴权失败不显示“重新下载”，每次自动重试不再重复刷相同 toast。用户文案同步中英文。

涉及：`play_url.rs`、播放错误契约、`use-playback-source.ts`、恢复组件、双语 locale；保留现有源 key、进度快照等竞态防御。

### C. 以真实分集和 vid 决定历史续播与下一集

1. 已在用户授权的隔离登录会话中完成 update → list →真实分集 `vid` 回环，恢复登录 update 的 0 基换算。内部模型与本地落库仍为 1 基；匿名上报按已实抓的 1 基发送，列表加一、删除换算和进度上传固定 0 均不改。不新增 service 编号修正层或批量迁移。
2. 历史入口使用 resolve 返回的分集表：有 `vid` 时按精确 vid 找到真实 `vidIndex`；没有 vid 时只接受表内存在的集号。vid 存在但不匹配时显示内容失效/重新选集，不静默改播另一集。
3. 选定合法目标后再记录续播目标，同时将历史的片内位置接入现有 `resumeHint`。不通过清历史、清库来“修复”已存在的问题记录。
4. ended、手动下一集、滚轮切集共用基于实际分集表的决策，返回下一有效分集、末集或资料未就绪三种结果，不再依赖列表长度或裸集号加一。
5. 相关季未就绪时等待，失败时提供重试；查询成功且确无后续季时才进入既有推荐逻辑。下一季首集同样从分集表确定。
6. 历史页、首页和详情共用按账号隔离的历史查询：匿名只读现有本地行，登录合并云端与同一本地行，按更新时间保留完整新记录。记录完成后主动刷新活跃查询，删除同步清理本地对应行。

涉及：`history/mod.rs`、公共 `history_service/listing.rs`、Tauri 的 `history_cmd.rs` 和 `service/queries/history.ts`、NSH 的历史页/个人内容源，以及历史续播、播放器 store、`use-binge-relay.ts`、`season.ts` 及相关纯函数。

### D. 恢复入口与媒体解码解耦，原生窗口统一提供真值

1. 将原有返回、退出小窗、选集等不依赖媒体的操作移出有源分支，报错时保持原控制栏。没有挂播放器的加载页也复用原窗口图标，不新增文字恢复按钮。只对播放/seek 等依赖媒体的操作禁用。
2. 键盘先处理输入框豁免、退出窗态、导航，再检查 video 并处理媒体操作；无源时 Escape 仍可恢复迷你窗口。
3. 以现有 `window_cmd::current_mode()` 为基础提供可读的原生窗口状态快照。AppShell 初始载入和 WebView 刷新时先同步模式，继续保持瞬态不写 localStorage。
4. 窗态切换串行完成，窗口 API 失败向上返回；成功后返回实际窗态，前端再更新镜像。失败时回读实际状态，保留可恢复的几何快照，不吞错误、不把半完成操作当成功。
5. 新增/调整 IPC 同步注册、命令封装、registry 和响应 schema；只围绕现有窗口行为收敛，不重写媒体渲染结构。

涉及：`window_cmd.rs`、`AppShell`、`stores/ui.ts`、`use-mini-window.ts`、键盘 hook、播放器操作组件及 IPC 契约。

## 同链路建议项

- `season.ts:59` 在当前作品存在但角标缺失时没有继续解析当前标题，可能错误地挑到较早季；`use-binge-relay.ts:50` 的按列表下一条回退还可能抵消按季号排序的规则。随 C 收敛为单一季号选择规则，无法判定时明示，不按乱序列表猜。
- 原历史页没有传递 `positionMs`，跨设备继续播放会丢失片内位置；已随 C 接入已有提示能力，没有增加另一套进度存储。
- 开发文档声称 invoke 有 30 秒超时，源码没有。随 A/B 更正文档与真实的任务取消/时限约定，不只给前端加一个留下后台任务的 `Promise.race`。
